## Executive summary

CallerFlash is **production-ready as a Windows desktop application**, with two meaningful caveats: `main` still has no branch protection, and the installer is not Authenticode-signed.

Since the last audit the application was fully rewritten onto Tauri 2 (Rust + rsipstack; the Electron/PJSIP stack is gone), the release pipeline was rebuilt (SHA-pinned actions, `release`-environment approval gate, build-provenance attestation, first-party `gh release create`), stable `v2.1.0` was published through that gated pipeline, and the dependency tree is clean (`npm audit`: 0 vulnerabilities; `cargo audit`: exit 0 with 17 documented informational ignores).

Application security posture remains strong: DPAPI at-rest credential encryption, strict IPC input validation with SSRF guards (unit-tested), per-command rate limiting, a single redaction chokepoint, least-privilege capabilities (separate `main`/`toast` capability files), strict CSP, minisign-pinned updater with an HTTPS host allow-list, single-instance enforcement, and close-to-tray lifecycle handling.

**Overall score: 76/100** at audit time — **raised to ~84/100 after the 2026-08-21 remediation pass** (coverage gates, SBOM, immutable update URLs, CSP tightening, truthful security docs, sanitized crash dumps, rate-limiter fix). Remaining open items are maintainer-accepted (branch protection, Authenticode) or low-severity hardening (F7/F11/F15).

### Still open

#### HIGH — declined by maintainer (accepted risk, single-maintainer project)

**F1 (remainder) — No branch protection on `main`.**
`GET /branches/main/protection` → 404. Anyone with write access can push directly to `main` and tag a release. The compensating controls are real (signing key only reachable behind the approved `release` environment; provenance attestation binds artifacts to the workflow run), which downgrades this from Critical to High. **Maintainer decision 2026-08-21: not applicable for a single-maintainer repo.**

**F3 — Installer is not Authenticode-signed.**
`tauri.conf.json` has no `signCommand`; the shipped `.exe` triggers SmartScreen "unknown publisher". Updater integrity is fine (minisign), but manual downloads are unverifiable to Windows and enterprises can't deploy via MDM. **Maintainer decision 2026-08-21: certificate cost not justified today.** Revisit if distributing beyond direct download.

## Threat model (current)

**Assets:** SIP credentials, caller-ID records, registration session, app config, update-channel trust, minisign signing key.

| Attack path | Mitigation | Gap |
|---|---|---|
| Remote XSS in WebView | Strict CSP (`script-src 'self'`, no external connect-src), `withGlobalTauri:false`, no remote content, sanitized caller-ID | `'unsafe-inline'` styles (React), no CSP violation reporting |
| Crafted INVITE from provider | Sanitize at parse exit; caller-ID-only (never answers); digest auth | No parser fuzzing |
| GitHub account compromise | Signing key behind approved `release` environment; provenance attestation; tag ruleset | No branch protection on `main` (F1 — accepted, single maintainer) |
| Local disk theft of settings.json | DPAPI (user-bound); password never in localStorage/logs | No HMAC on non-secret fields (F11, accepted-risk candidate) |
| Malicious update endpoint | Immutable per-tag URLs + HTTPS host allow-list + pinned minisign pubkey | — |
| Compromised renderer spams IPC | Per-command rate limits (poisoning-tolerant) + validation + 64KB toast cap | — |
| Tampered installer (manual download) | SHA256SUMS published per release | No Authenticode (F3 — accepted, cert cost) |
